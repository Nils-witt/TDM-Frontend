# universamFrontend

Vite + React 19 (TypeScript) single-page application. Its base structure is copied from `missioncontroller/web`, without domain widgets. It is the frontend of `universalGoApi`, which runs on a separate origin.

## Layout

- `src/main.tsx` renders `app/App.tsx`, the auth gate. Once signed in it renders `app/Shell.tsx`: `ResourceProvider` → `EventsProvider` → `DataProvider` → `LayoutProvider` → `DashboardProvider` → `SelectedMissionProvider` → `WidgetWindows` → `Nav` + `Dashboard`.
- Routing (React Router, `react-router`): the `BrowserRouter` is mounted in `App.tsx` only once signed in, as `startSession` may first replace the URL with the login's return path. `/m/*` renders `responsive/ResponsiveShell.tsx`, everything else the desktop `Shell`. `main.tsx` sends small touch screens opening `/` to `/m` (before the session starts, so a login returns there) unless `localStorage` `universam.preferDesktop` is set (`app/mobileRoute.ts`) (set by the responsive Settings page's Desktop view); the desktop's Universam → Responsive View (action `mobileView`) clears it.
- `src/responsive/`: a responsive UI independent of the dashboard. It shares the data layer (`ResourceProvider` → `EventsProvider` → `DataProvider`, `src/api`, `src/data`), generic components and some widgets, but no dashboard, layouts, `DashboardContext` or selection. `AppFrame` has a header with the `LiveIndicator`, `BackupStatus` (the menu bar's `BackupIndicator` for phones: hidden unless enabled, colored by `summarizeBackup`; a tap opens the lazy `BackupStatusDialogMUI`, full screen on phones, with the same instances, jobs, expandable targets and Refresh; titles and labels shared in `nav/actions/backupLabels.ts`) and one nav that is a bottom tab bar on phones and a sidebar from 768px. `WidgetSheets` supplies `WidgetWindowContext`: what a widget opens in a window is a full-screen sheet kept in the history entry's state, so Back closes it. `EmbeddedWidget` shows a registered widget in a frame-like card that grows with the page. Routes (relative to `/m`, built with `paths.ts`): `missions` (`pages/MissionsPage`: search and status filter (Active, Done, Closed, All) kept in the URL as `?q=` and `?status=`, and a New button, disabled offline), `missions/new` (`pages/NewMissionPage`: `MissionFormMUI` without a mission, which creates one; the created mission's page then replaces it in the history), `missions/:id` (`pages/MissionPage`: a Show on map link (`paths.missionOnMap`, to `map?mission=`) for a mission with `address_coordinates`, the Mission Details widget's `MissionForm` for the mission in the URL, then the `LogbookForm` (`showMission: false`) and `Logbook` (`showCreate: false`) widgets (stacked; from 1100px the form left, the logbook right), given that mission through `SelectedMissionContext` with `useMissionData(id)`), `map` (`pages/MapPage`, lazy-loaded: the Map widget's `MissionMap` with its default options; tapping a pin keeps the mission in `?mission=` and shows a card linking to its page; it opens on the view it was left at, kept in `localStorage` (`universam.mapView`, `mapView.ts`) through `MissionMap`'s `onViewChange`). `archive` (`pages/ArchivePage`: the Mission Archive widget's `MissionArchiveMUI`; its filter, sort and page are kept in the URL (`MissionArchiveMUI/archiveUrl.ts`, passed to `useMissionArchive` as `state`), so Back from a result restores the search; a result opens the mission's page), `reports` (`pages/ReportsPage`: the Reports widget's `ReportsMUI` with Create, Upload signed and Share… as MUI dialogs; `?mission=` (`paths.missionReports`, the Reports link on a done or closed mission's page) filters by it and is the mission Create offers first), `settings` (`pages/SettingsPage`: account details from whoami, Map overlays, Desktop view, Log out). `ArchivePage`/`ReportsPage` are one `EmbeddedWidget` (`showHeading={false}`) below the page heading. The map's overlays are switched on the Settings page, not on the map: `overlaySettings.ts` keeps them in `localStorage` (`universam.mapOverlays`) and `MapPage` passes them as `overlayControl`. `MissionMap` takes `selectedId`/`onSelect` and an optional `overlayControl` (without it, its own state and switcher, as on the dashboard); the dashboard's `Map` widget wraps it with `useDashboard()`. A new page gets a route in `ResponsiveShell`, a path in `paths.ts` and, if it is a section, an entry in `AppFrame`'s `sections`. Widgets on `/m` are MUI (`@mui/material` 7 + emotion, styled with `sx`; icons stay `SymbolIcon`); the desktop does not use MUI. `src/responsive/widgets/` holds a `<Name>MUI` variant per widget used there (`MissionDetailsMUI` (`MissionFormMUI` only, used by `MissionPage`; the desktop wrapper needs `useDashboard()`), `LogbookFormMUI`, `LogbookMUI` (a visible Revoke button per entry instead of the context menu), `AttachmentViewerMUI`, `PdfViewerMUI`, `MissionArchiveMUI`, `ReportsMUI` (with `CreateReportDialogMUI`, `SignReportDialogMUI`, `ShareReportDialogMUI` on `shared/DialogsMUI`'s `DialogShell`, full screen on phones for `maxWidth="sm"`)) and their MUI inputs in `shared/`. They import the desktop widgets' hooks and helpers (`useMissionForm`, `useLogbookFormWidget`, `useLogbookWidget`, `logbookCommands`, `useAddressSuggest`, `useBlobContent`, `useMissionArchive`, `useReportsWidget`, `useCreateReport`, `useSignReport`, `useShareReport`, …) and only render differently, so a behavior change goes into the shared hook. `widgets/registry.ts` keys them by the desktop ID, reusing its metadata; `responsiveWidget(id)` (used by `EmbeddedWidget` and `WidgetSheets`) returns the MUI variant, else the desktop widget, so `openWidget('AttachmentViewer')` opens the MUI one on `/m`. The theme (`widgets/theme.ts`, colors from `_tokens.scss`, light/dark by system) is provided by `widgets/ThemeScope.tsx` and, like `MissionFormMUI`, loaded lazily so MUI stays out of the desktop's bundle. `_forms.scss`'s bare `input`/`select`/`textarea` rules skip elements with `Mui*` classes (via `:where`, keeping their specificity), as MUI's dialogs and poppers portal outside any route root.
- Auth (`src/auth/session.ts`, oidc-client-ts):
  1. The login page offers Authentik or a client certificate. The certificate button calls `GET /api/v1/whoami` without a token on the mTLS API URL; a 200 means an mTLS reverse proxy authenticated the certificate (`mode: 'proxy'`), and that URL is used from then on. The choice is kept in sessionStorage (`universam.clientCertificate`) so a reload re-checks it instead of showing the login page; Log Out and any 401 forget it. The mTLS URL is never contacted without the button, since a browser may prompt for a certificate.
  2. Otherwise it uses the Authentik authorization code + PKCE flow, configured from `GET /auth/config`. The redirect URI is `<origin>/callback`, and tokens are kept in sessionStorage.
  3. Tokens are renewed in the background with the refresh token, which needs the `offline_access` scope in the API's `OIDC_SCOPES`. Without one, the session ends when the token expires. `session.ts` renews it itself (oidc-client-ts's `automaticSilentRenew` is off): a timer fires ahead of expiry, by half the token's lifetime but at most 2 min. A network error is retried with backoff (5–60 s). It checks again on `focus`, `online` and when the tab becomes visible, since timers run late in background or sleeping tabs. `send()` in `client.ts` waits for a renewal (`setTokenRefresh`) before a request whose token has expired. Only one renewal runs at a time, because Authentik rotates refresh tokens.
  4. Logging out uses the provider's `end_session_endpoint`.
  5. Any 401 shows the login page again.
- `useSession()` (`app/session.ts`) returns `{ principal, mode, logout }`. `isAdmin(principal)` / `useIsAdmin()` read `permissions` from whoami (`admin` for members of the API's `ADMIN_GROUP`; absent = none).
- `src/api/`: `layouts.ts` (dashboard layouts and the user's preferences), `client.ts` (`request` prefixes the API URL from `/config.json`, loaded by `main.tsx` before rendering: `apiBaseUrl` for OIDC (else `VITE_API_BASE_URL`), `mtlsApiBaseUrl` for client certificates (else `apiBaseUrl`); sends `credentials: 'include'` and the Bearer token, throws `ApiError` with the RFC 9457 `detail`), `auth.ts` (`/auth/config`, `/api/v1/whoami`), `directory.ts` (users, groups, members), `audit.ts` (`auditLogPath`), `address.ts` (address suggestions from `/api/v1/address/{streets,house-numbers,cities,districts,geo-objects}`; the Object field suggests the directory's geo objects, and picking one replaces street, house number, city, district and position, and `reverseGeocode`, the address at a coordinate from `/api/v1/address/reverse` (the nearest address and nearest geo object): a geo object within 25 m (its name and address), else a house number within 50 m, else null; `nearbyPlaces`, the geo objects and house numbers nearest to a coordinate (`?limit=`) with their distance, behind the Mission Details' button beside Lat / Lon (`shared/NearbyPlaces.ts`, `NearbyPlacesButton`, `NearbyPlacesButtonMUI`), whose pick fills in the address but keeps the coordinates; a 404 turns them off until reload), `resource.ts` (`useResource(path)`: a shared, coalescing cache that loads when first shown, on `reload()` and on change events), `EventsProvider.tsx` + `events.ts` (live updates: a WebSocket to `GET /api/v1/events` (`websocketUrl` in `client.ts`) on which the API announces the entity types (table names) that changed; `changedPaths` maps them to API paths and `cache.reloadShown` reloads the shown ones, everything after a reconnect or `resync`. With OIDC the first message is `{"type":"auth","token":…}`, resent after each renewal (`accessTokenRenewed`), as a browser cannot set the Authorization header on a WebSocket; the client certificate proxy authenticates the upgrade itself. It reconnects with backoff; `LiveIndicator` in the menu bar (and the responsive UI's header) always shows the connection state: green when connected, red while disconnected). A new API entity type needs an entry in `typePaths`; unknown types reload everything, `setting.ts`, `maps.ts` (map styles: `useMapStyles()`, `resolveMapStyle`, `mapStylesApi`; overlays proxied by the API from its tile server: `useOverlays()`, `fetchOverlayBounds`, `overlayTilePath`; the admins' map defaults: `useMapSettings()`, `useDefaultOverlayStates()`). `useResource(path, fetcher)` takes an optional module-level fetcher; `list.ts` (`requestAll`, `listFetcher`) follows `next_before` through every page, and `collection.ts` (`useCollection`) turns a list into `{ items, byId, loading, error, reload }`. Types and paths per entity: `entity.ts`, `catalogs.ts` (plus `*Api` create/patch/remove for admins), `missions.ts`, `logbook.ts`, `tasks.ts`, `exportTemplates.ts` (`useExportTemplates()`, `exportTemplatesApi` incl. `preview`, `missionExportPath`), `reports.ts` (`useReports(filter)`, `reportsApi.create`/`sign`, `reportPdfPath`), `workflows.ts` (`useWorkflows()`, `useWorkflowCatalog()`, `workflowsApi`; admins only), `backup.ts` (`useBackupStatus()`: `GET /api/v1/backup-status`, which the API proxies from every go-backup-tool instance admins configure (`instances`, each with its shown `jobs` or an `error`), so the tokens stay on the server; polled every 60 s since go-backup-tool has no events; `summarizeBackup` gives `good`/`degraded`/`failed` across the instances, an unreadable one counting as one failure; `useBackupInstances()`, `backupInstancesApi` for `/api/v1/backup-instances` (admins only; the token is write-only, `has_token` says whether one is stored, a patch without it keeps it)). `/api/v1/users` is readable by every user (the Reports widget names signers with it).
- `src/data/`: API data for widgets and the responsive UI. `useMissionTypeName(id)` gives "Group / Type". `useCatalogs()` (mission type groups, mission types, logbook types, file types) and `useMissions()` load once signed in, from the replica (`useTable`, see Offline mode). Missions are synced per status (`missions?status=…`, the API filters by one): `useMissions()` gives the ones not closed; `useMissions({ closed: true })` adds the closed ones, loaded only while such a caller is shown (Mission Archive, Reports, Create Report, the template preview, a Missions list without Hide "Closed" (default on), a Map with Show "Closed" (default off), `/m`'s All and Closed filters; Active is its default). `useMission(id)` finds one mission of any status, loading the closed ones only for an ID not among the others; one closed more than 24 h ago (the list leaves those out, the archive finds them) is fetched with `GET /api/v1/missions/{id}` (`useResource` with `persist: false`) and reported as `transient`; `useMissionData` uses it and loads such a mission's log entries, files and tasks in transient replica scopes (`scopeKey(table, id, { transient: true })`), kept in memory only, never in IndexedDB; their attachments' content paths are passed to `keepContentOut` (`offlineStore.ts`), so `requestCachedBlob` neither stores nor reads them. `useSelectedMission()` gives `{ mission, logEntries, logFiles, tasks }` for the dashboard's `selectedId` (mission null if it isn't a mission). `useMissionData(id)` gives the same for any other mission. The admin endpoints (users, groups, audit log) are loaded only by the admin widgets. Changes made elsewhere arrive through the event stream; still call `reload()` (or `cache.put`) after a write, so the writer sees it without waiting for the event.
- `src/components/`: generic UI (`Alert`, `Spinner`, `ConfirmDialog`, `SuggestInput`, `form/`, `menu/`, `symbols/`, `widgetWindow/`).
- `src/nav/`: macOS-style menu bar (`Nav.tsx`), `NavMenuItem` with `action` / `widget` / `href`, actions in `navActions.ts`, keyboard shortcuts in `shortcuts.ts`, the View menu (layouts), and the About, Clock, Fullscreen and channel indicators, and `actions/BackupIndicator` (hidden unless the API's backup status is `enabled`, i.e. an instance is configured: an icon colored by `summarizeBackup` whose menu has a heading per instance (its own summary dot and error) with its jobs below, each with state and last run; clicking a job shows its targets with state and error below it; and Refresh). Menus follow missioncontroller's: Missions (Map, Save ⌘S via `widgets/MissionDetails/missionSave.ts`, Clear, Close via `MissionCloseProvider`, which PATCHes `status: closed`; there is no reopen; Intermediate Report… ⌘P (action `printMission`) via `MissionPrintProvider`, whose `IntermediateReportDialog` picks an export template, POSTs `/api/v1/missions/{id}/intermediate-report` (`intermediateReport` in `api/exportTemplates.ts`) for a mission in any status, and opens the PDF in a `PdfViewer` window. Layouts are stored by the API (`api/layouts.ts`, `/api/v1/layouts`): `global` ones (shown as Shared) are seen and used by everyone, `group` ones by the members of their `groups` (group names as in whoami's `groups`); both are written by admins. `user` ones exist only for their owner. Each user's default layout, the same in every browser, is `default_layout_id` of `/api/v1/me/preferences` (View → Use as My Default; null = the built-in layout). Layouts an older version kept in localStorage (`universam.layouts`, with the browser's default) are uploaded as the user's own on sign-in and then removed (`localLayouts.ts`). There is an edit mode with undo/redo and import/export, multi-monitor arrangements, and channels (BroadcastChannel) that share the `selection` event (`selectedId` in `dashboardContext`).

- PWA (`vite-plugin-pwa`, configured in `vite.config.ts`): a Workbox service worker precaches the app's own build output, OCR assets in `/ocr/` included (~24 MB; `maximumFileSizeToCacheInBytes` 8 MiB), and serves `index.html` for navigations (not `/api/`, `/auth/`). It caches no API data (the app keeps its own, see Offline mode); `/config.json` is NetworkFirst (cache `config`) so the last copy works offline; map styles, sprites, glyphs and tiles (every other origin except `/api/`, `/auth/` and Authentik's `/application/`, `/if/` paths, plus `/api/v1/overlays/`) are StaleWhileRevalidate in cache `map-tiles` (24 h, 3000 entries). `registerType: 'prompt'`: `app/update/UpdatePrompt.tsx`, mounted in `App.tsx` (login page included), shows a Later/Reload notice when a new build is found (on page load only), with `responsive/UpdatePromptMUI.tsx` (lazy, a top Snackbar) on `/m`. The manifest (`start_url: /m`, theme `#1976d2`) and its icons are generated at build from `public/favicon.svg` (`pwaAssets`). No service worker in `make dev`.
- Offline mode (read-only): `api/connectivity.ts` counts the app offline while the event WebSocket is down or the last request got no answer (`useOffline()`, `offline()`); `send()` in `client.ts` then refuses non-GET requests. `api/offlineStore.ts` (IndexedDB via `idb`, database `universam-offline`, version 3) replicates the API's mission-domain tables (universalGoApi's `00004_missions.sql`): one store per table, named like it and like the event types (`missions`, `mission_type_groups`, `mission_types`, `logbook_types`, `file_types`, `log_entries`, `log_files`, `tasks`), holding the API's rows keyed by `id`, with the table's indexes (`mission`, `entry`, `digest`, `group_id`, missions' `status`; database version 3). `syncs` records when each scope was last synced. File contents loaded through `requestCachedBlob` are kept in `blobs` keyed by digest, as in the API, for log files the replica knows, so equal attachments are stored once. Others (report PDFs) go in `contents` by path; both stores share 100 MB, oldest evicted. `resources` keeps every other `useResource` path (the cache is created with `persist: true`: the stored copy shows until the first load answers; a load without an answer keeps the data without an error). `meta` keeps the last signed-in principal with the auth config. Scopes not synced for 24 h are dropped with their rows, and so is everything else older than that. `api/replica.ts` reads the mission domain local-first. `useTable<T>(scopeKey(table, value?))` (`useTables` joins several scopes of one table) returns a `Collection` of the stored rows at once and syncs the scope when first shown and on `reload()`: one `requestAll`, after which rows the API left out (revoked, deleted) are removed. `EventsProvider` calls `replica.syncShown(types)`. `replica.put`/`remove` apply a write's result (the Logbook removes a revoked entry and its files). The shown rows are also kept in memory, so the app works where IndexedDB is blocked. `ResourceProvider` provides the replica (`useReplica()`). `data/OfflinePrefetch.tsx` (in `DataProvider`) subscribes to the logbook, files and tasks of every mission that is not closed, so events keep them current, and downloads the contents of their attachments one at a time, skipping digests already stored. When `startSession()` gets no answer (network error, not an `ApiError`), it signs in as the stored user with `offline: true`; `App` then rechecks every 15 s, and on a 401 or token expiry starts the session again before ending it. Log Out, a 401 that ends the session, and another user signing in call `clearOffline()` (IndexedDB and the `map-tiles` cache). While offline `readOnly` of `useMissionData` / `useMissionForm` is true, the map's context menu does not open, the write actions of the nav, View menu, Reports and admin widgets are disabled, and `components/OfflineBanner` shows the time of the last API answer (floating on the desktop, at the top of `/m`'s content).
- `src/styles/`: design tokens and global partials (copied from missioncontroller, `_logbook.scss` included), pulled in by `src/index.scss`. Components use `*.module.scss`; forms are in the Mission Details style (`components/form`: `Section`, `FieldRow`, `FormActions`, errors below the actions).
- `@/` is an alias for `src/`.

## Conventions

- Context: `createContext<T | null>(null)`, read with `use()` in a hook that throws outside its provider.
- Comments explain why. Don't restate names.
- Adding a widget: create `widgets/<Name>/<Name>.tsx` (default export taking `WidgetProps`), register it in `registry.ts`, and optionally add a `NavMenuItem` and shortcut.

## Commands

- `make dev`: Vite dev server on port 5173 (fixed, because the redirect URI and CORS depend on it). The API is at `VITE_API_BASE_URL` (`.env.development`: `http://localhost:8080`).
- Authentik: register `http://localhost:5173/callback` (and the production `<origin>/callback`) as redirect URIs. Add the SPA origin to the API's `CORS_ALLOWED_ORIGINS`.
- `make build`: `tsc -b && vite build` into `dist/`.
- `make lint` (oxlint), `make fmt` / `make fmt-check` (Prettier, `.prettierrc.json`).
- `make docker API_BASE_URL=https://api.example.com`: nginx image that serves `dist/` and falls back to `index.html`. Set the API origin at runtime by mounting a `config.json` (`{"apiBaseUrl": "https://api.example.com", "mtlsApiBaseUrl": "https://mtls.api.example.com"}`) at `/usr/share/nginx/html/config.json`. `API_BASE_URL` is an optional build-time fallback.
