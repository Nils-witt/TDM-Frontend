# src/pages/dashboard/widgets

Part of the root `CLAUDE.md` (Layout), kept here so it loads with this directory.

- `src/pages/dashboard/widgets/`: `registry.ts` (metadata plus a `lazy()` component per widget), `widget.ts`, `widgetOptions.ts`, `widgetCategories.ts`. `Example/` is the template for new widgets. A widget's own view settings (not its layout `options`) use `useWidgetState(name, initial, parse)` (`widgetState.ts`): like `useState`, but kept in sessionStorage (`universam.widgetState.<window name>.<layout>.<monitor>.<item id>.<widget>.<name>`), so each widget of a layout keeps its own across reloads, even several of one kind; a layout item's `id` (`layout.ts`) is unique within its monitor and set when it is added (`defaultItem`); an item stored without one is known by its position (`itemIds`) until editing stores the IDs (`withItemIds` in `startEdit`/`startImport`); `Dashboard`'s frames provide the key through `WidgetInstanceContext`, and without one (windows, `/m`) it is memory only. The Map keeps its overlay switches and zoom on selection there. Widget actions go in the action bar above the content (`shared/WidgetActionBar`: `WidgetActionBar`/`WidgetAction`, `WidgetActionSelect` for a select sized to the bar (the global form style is taller), portaled into `WidgetBody`'s slot); a form's Save/Add/Discard use `FormActionBar` (MUI: `FormActionBarMUI` in `responsive/widgets/shared/ActionsMUI.tsx`, inline where there is no slot), whose submit button targets the form by `id`, as in Mission Details and Logbook Form; the Map's Options is there too. `MissionArchive` searches missions by any field or by event, status, type group/type, address parts, callee, tag, assigned unit (name, call sign or ID of any unit ever on the mission, released ones included; offline from the stored `mission_units` scopes, read only while that filter is set; the field suggests the units server's units by call sign or name, `useUnitSuggestions` in `MissionArchive/unitSuggestions.ts`, loaded once it is focused, on `SuggestInput` and on `/m` `AddressFieldMUI`) and creation date through `GET /api/v1/missions/search` (`missionSearchPath` in `api/missions.ts`: every status, closed ones of any age included, which the synced missions lack; sorted (`sort`/`order`) and paged (`page`/`page_size`, `total`) by the API; reloaded on mission events), and while offline in the browser over the stored missions, sorted and paged the same way; it lists nothing, only a hint, until a field other than status is set (`hasSearch`; nothing is loaded meanwhile, offline included, so a `status` option alone shows no list), then one page of 50 matches in a sortable table with a pager (the last page stays shown, dimmed, while the next loads); a row click selects the mission; option `status` is the status filter it starts with. `useMissionArchive({ initialStatus, state? })` (`MissionArchive.ts`) does not read the dashboard (the widget selects the clicked row itself) and keeps its query (`ArchiveQuery`: filter, sort, page) in `useState` unless a caller passes `state`.
