# src/pages/dashboard/widgets

Part of the root `CLAUDE.md` (Layout), kept here so it loads with this directory.

- `src/pages/dashboard/widgets/`: `registry.ts` (metadata plus a `lazy()` component per widget), `widget.ts`, `widgetOptions.ts`, `widgetCategories.ts`. `Example/` is the template for new widgets. A widget's own view settings (not its layout `options`) use `useWidgetState(name, initial, parse)` (`widgetState.ts`): like `useState`, but kept in sessionStorage (`universam.widgetState.<window name>.<layout>.<monitor>.<item id>.<widget>.<name>`), so each widget of a layout keeps its own across reloads, even several of one kind; a layout item's `id` (`layout.ts`) is unique within its monitor and set when it is added (`defaultItem`); an item stored without one is known by its position (`itemIds`) until editing stores the IDs (`withItemIds` in `startEdit`/`startImport`); `Dashboard`'s frames provide the key through `WidgetInstanceContext`, and without one (windows, `/m`) it is memory only. The Map keeps its overlay switches there. Widget actions go in the action bar above the content (`shared/WidgetActionBar`: `WidgetActionBar`/`WidgetAction`, portaled into `WidgetBody`'s slot); a form's Save/Add/Discard use `FormActionBar` (MUI: `FormActionBarMUI` in `responsive/widgets/shared/ActionsMUI.tsx`, inline where there is no slot), whose submit button targets the form by `id`, as in Mission Details and Logbook Form; the Map's Overlays toggle is there too. `MissionArchive` searches missions by any field or by event, status, type group/type, address parts, callee, tag, assigned unit (name, call sign or ID of any unit ever on the mission, released ones included; offline from the stored `mission_units` scopes, read only while that filter is set; the field suggests the units server's units by call sign or name, `useUnitSuggestions` in `MissionArchive/unitSuggestions.ts`, loaded once it is focused, on `SuggestInput` and on `/m` `AddressFieldMUI`) and creation date through `GET /api/v1/missions/search` (`missionSearchPath` in `api/missions.ts`: every status, closed ones of any age included, which the synced missions lack; sorted (`sort`/`order`) and paged (`page`/`page_size`, `total`) by the API; reloaded on mission events), and while offline in the browser over the stored missions, sorted and paged the same way; it lists one page of 50 matches in a sortable table with a pager (the last page stays shown, dimmed, while the next loads); a row click selects the mission; option `status` is the status filter it starts with. `useMissionArchive({ initialStatus, state? })` (`MissionArchive.ts`) does not read the dashboard (the widget selects the clicked row itself) and keeps its query (`ArchiveQuery`: filter, sort, page) in `useState` unless a caller passes `state`. Ported from missioncontroller and adapted to universalGoApi: `MissionsList`, `MissionDetails`, `ActiveMissions`, `Logbook`, `LogbookForm`, `FileList`, `AttachmentViewer` (window only), `Reports` (the reports the caller sees: admins all, others those they created, sign, or that are shared with them or their groups; create from a done or closed mission, upload the signed PDF once with user or external signers; the creator or an admin shares a report with users and groups via `ShareReportDialog` (`reportsApi.share`, `PUT /api/v1/reports/{id}/shares`; non-admins are offered their own groups, as `/api/v1/groups` is admin-only); its state is `useReportsWidget(selectedId)` (`Reports.ts`), the dialogs' `useCreateReport`, `useSignReport`, `useShareReport`, shared with the responsive variants), `UnitStatus` (category General, Units → Unit Status: the latest FMS status changes, newest first, as from → to badges colored by `fmsTone`, a request's badge dashed and marked with the status the unit stays on; option `limit`, 1–500, default 50; a function filter that looks up each change's unit in `useUnits()`, as the changes carry no function, so it applies to the `limit` latest changes. The unit widgets' function filter is the Logbook's kind: a Filters toggle in the action bar (with the active count) shows a Filter section whose checkbox list (`shared/UnitFunctionFilterInput.tsx`, `UnitFunctionFilterSection.tsx`) picks function codes, "No function" included, empty = all; `useUnitFunctionFilter` (`shared/unitFunctionFilter.ts`) keeps them with `useWidgetState`, starting from option `filterFunctions` (comma-separated codes); a warning while the API is not connected to the units server), `UnitRequests` (category General, Units → Unit Requests: the pending requests, newest first, each acknowledged by clicking its row (or Enter/Space on it) and confirming (not offline or while the API is not connected to the units server); once acknowledged, if the unit is on a mission (`useActiveMissionUnits`), that mission is selected and a `LogbookForm` window opens with the unit as sender (LogbookForm's option `sender`, passed to `useLogbookFormWidget`), a 0 highlighted; the acknowledged ones dimmed below behind the action bar's Acknowledged toggle (`useWidgetState`); the function filter; its state `useUnitRequests(fns)` in `UnitRequests/unitRequests.ts`, shared with the indicator), `MissionUnits` (Units → Units in Mission: the selected mission's units with their live FMS status (`useUnits()`), Release in a current row's context menu (right click, or the context-menu key on the focused row), released ones dimmed below (the action bar's Released toggle, `useWidgetState`), and Add Unit… opening `AddUnit` in a window) and `AddUnit` (Units → Add Unit…: the units server's units with a search, Assign for a free one; one on another mission names it, a click selecting that mission), `UnitScopes` (category General, Units → Unit Scopes: the units with a scope select each (Default plus the catalog's scopes, saved on change, disabled offline), a search, a scope filter (`useWidgetState`) and the function filter). Add Unit, Unit Status and Unit Requests have the option `currentScopeOnly` (`unitScopeOption`, default on; `shared/unitScopeFilter.ts`, `useUnitScopeMatch`): only the units in the tab's scope (`useSelectedScope()`), Default showing the units in none; Add Unit's action bar has an All Scopes toggle (`useWidgetState`, starting from the option) that lists every scope's units; the menu bar's `UnitRequestIndicator` always follows the tab's scope; Units in Mission is not filtered; both filter by the unit's function (the tactical name's function code, `function` of `/api/v1/units`, else the assignment's `unit_function`), as Unit Status does, their state in `MissionUnits/missionUnits.ts` (`useMissionUnits`, `useAssignUnit`), the FMS badge shared with Unit Status in `shared/FmsBadge.tsx`, `BackupStatus` (category General, for every user: the menu bar's backup status as a widget, a table of jobs per instance with state, last and next run, interval and size, a click on a row showing its targets; Refresh in the action bar; opened from the `BackupIndicator` menu's Show in Window and Admin → Backup Status), `PdfViewer` (window only; options `path`, an API path loaded with `requestBlob` through `shared/blobContent.ts`, as for `AttachmentViewer` (report PDFs need the token), or `document`, the key of an already fetched intermediate report in `shared/pdfDocuments.ts`, gone after a reload; and `name`), `Map` (MapLibre, `maplibre-gl`: missions with `address_coordinates` as pins colored by status, click selects; the context menu (`MissionMap`'s `onContextMenu`, a right click or long press; the actions in `mapActions.ts` (`useMapActions`), rendered by the dashboard widget and, in MUI, by `/m`'s `MapPage`, where the selected mission is `?mission=`) creates a mission at the clicked position (asking for the occurred event) and selects it, or sets the selected mission's `address_coordinates` there (not for a closed one); opening the menu reverse-geocodes the position, and a found address replaces street, house number, city and district, and a found geo object also the object name (without one, it stays); option `style` (type `mapStyle`) picks a map style by ID, empty = the default; option `only-selected` (default off) shows only the selected mission's pin, overriding the `show-<status>` options; option `show-unsaved` (default on) shows a mission's unsaved Mission Details edits (position, status, title) on its pin, drawn dashed: `useMissionForm` registers them in `MissionDetails/missionDrafts.ts` (this window only); option `show-units` (default on) shows the units server's units at their last known `position` (`/api/v1/units`, which the API passes through from the units server) as their tactical symbol (`symbol` and `tactical_name`, passed through from the units server, rendered with `@taktische-zeichen/core` as the units server's UI does, cached per symbol, in `shared/unitSymbol.ts`) with their FMS status (colored by `fmsTone`) in a corner, or without a symbol as a chip of status and short call sign, below the mission pins (`useMapUnits` in `Map/Map.ts`); a unit on a mission (`?active=true` mission units) selects it when clicked and is ringed while it is selected; only-selected keeps the selected mission's units, `currentScopeOnly` the tab's unit scope (`useUnitScopeMatch`); an overlay switcher when the API has a tile server. MapLibre loads the overlay tiles itself, so `transformRequest` adds `authHeaders()` from `api/client.ts` to `/api/v1/overlays/` URLs only). Admin widgets (`adminOnly` + `hiddenInPicker`, opened from the Admin menu; `WidgetContent` shows non-admins a notice instead): `MissionTypes` (groups + types; a type has a `description`, edited there (`CatalogManager`'s `describe`) and shown below the type field (`MissionTypeDescription`, the MUI field's helper text and menu). The type field (`MissionTypeInput` on `SuggestInput`, `MissionTypeInputMUI` on MUI's `Autocomplete`, sharing `shared/missionTypeOptions.ts`) is one text field for group and type: typing matches every word against group, type and description, and the type is set once the text names one ("Group / Type" or a name unique across groups); CSV import/export in `missionTypesCsv.ts` (columns `group,type,description`), which creates what is missing and, if the file has the column, updates descriptions, never renaming or deleting), `LogbookTypes`, `FileTypes`, `Scopes` (all via `shared/CatalogManager`, which reloads the shared `useCatalogs()` collection after a write), `Users`, `Groups` (read-only, LDAP), `Permissions` (the grantable permissions from `GET /api/v1/permissions`, checked per group and saved with `PUT /api/v1/groups/{id}/permissions` (`api/permissions.ts`); an implied permission (`impliedPermissions`, mirroring the API) shows checked and disabled; option `groupId`, set by Groups' Permissions button), `MapStyles` (name, https style URL, one default), `MapAdmin` (Admin → Map Defaults: the default map style, saved as Map Styles' `is_default`, and the overlays every map starts with, `default_overlays` of `GET/PUT /api/v1/map-settings` (`useMapSettings`, `mapSettingsApi` in `api/maps.ts`); `MissionMap` and `/m`'s Settings put `useDefaultOverlayStates()` beneath their own overlay state, so a user's switch wins), `ExportTemplates` (pongo2 sources in a CodeMirror editor, `codemirror` + `@codemirror/lang-jinja`, with a live preview of a picked mission through `POST /api/v1/export-templates/preview` in a sandboxed iframe, optionally as an intermediate report (`is_intermediate`, with the watermark); the variables are listed in `VariablesReference.tsx`), `Workflows` (Admin → Workflows: the rules the API runs on its own when missions and tasks change, units are assigned or released, or a unit's FMS status changes (triggers Unit assigned, Last unit released, Unit status changed, action Release unit; FMS status lists are the param type `fms_statuses`, checkboxes labeled with `fmsStatusLabels`), ported from missioncontroller; a list with an enabled toggle, and a React Flow graph editor (`@xyflow/react`, only in the widget's lazy chunk) with a palette of the catalog's triggers, filters and actions from `GET /api/v1/workflows/catalog`, the canvas, and `NodeParams` for the selected node; `graph.ts` converts between the API's graph and React Flow's nodes and edges and lists the context paths a node may refer to; the API records a workflow's changes as `workflow:<name>`), `ConfigTransfer` (Admin → Import / Export…: the admins' configuration as one JSON file (`configBundle.ts`, `format: universam-config`, version 2): mission type groups and types (each `{ name, description }`; empty on edit keeps the stored one) and the shown jobs (comma-separated, empty = all)), `Layouts` (every user's layouts from `GET /api/v1/layouts?all=true`: rename, Share… (`ShareDialog`), export, history, delete; a write also reloads the View menu's list), `AuditLog` (Newer/Older pages; options `entityType`/`entityId`/`actor` are its starting filter). They link to each other through `openWidget` options. The `selection` (`selectedId`) is a mission ID. A closed mission is read-only in every widget (`readOnly` from `useSelectedMission()`). `shared/` holds their common parts: address autocomplete for Mission Details (`AddressSuggest.ts` + `components/SuggestInput`), `/now`, `/me`, `/callee` commands (`logbookCommands.ts`, `CommandField`), in-browser OCR of attachments (`ocr.ts`, tesseract.js; its assets are copied into `public/ocr/` by `scripts/copy-ocr-assets.mjs` on `predev`/`prebuild`). File content needs the token, so it is loaded with `requestBlob` (`api/client.ts`), never as a plain link. Revoked log entries are not loaded. A log file can be pinned to its mission, shared by every user (`pinned_at`/`pinned_by`; `pinLogFile` in `api/logbook.ts`, `PUT`/`DELETE /api/v1/log-files/{id}/pin`, not for a closed mission): `shared/filePin.ts` (`useFilePin`, which puts the answer into the replica, and `pinnedFirst`) backs the pin button of `LogFileList` and `LogFileListMUI` (with `canPin`, i.e. not read-only; otherwise a pinned file only shows the pin), used by Logbook and FileList; FileList lists pinned files first.
