# src/data

Part of the root `CLAUDE.md` (Layout), kept here so it loads with this directory.

- `src/data/`: API data for widgets and the responsive UI. `useMissionTypeName(id)` gives "Group / Type". `useCatalogs()` (mission type groups, mission types, logbook types, file types, scopes) and `useMissions()` load once signed in, from the replica (`useTable`, see Offline mode). Missions are synced per status (`missions?status=…`, the API filters by one): `useMissions()` gives the ones not closed; `useMissions({ closed: true })` adds the closed ones, loaded only while such a caller is shown (Mission Archive, Reports, Create Report, the template preview, a Missions list without Hide "Closed" (default on), a Map with Show "Closed" (default off), `/m`'s All and Closed filters; Active is its default). Mission scopes (not a layout's `scope`): admins keep a catalog `scopes` (`/api/v1/scopes`, `MissionScope`, `scopesApi`, `useCatalogs().scopes`; Admin → Scopes, the `Scopes` widget on `CatalogManager`); a mission's `scope` is its ID, null for the implicit Default scope, which has no entry. `useSelectedScope()` (`data/selectedScope.ts`, `SelectedScopeProvider` in `DataProvider`, so both UIs have it) is the tab's scope, kept in sessionStorage (`universam.missionScope`, a new tab starts in Default; a deleted scope falls back to Default once the catalog is loaded), picked in the menu bar's `nav/actions/ScopeMenu` and `/m`'s header (`responsive/ScopePicker`, lazy `ScopeMenuMUI`). Global, listed first in the pickers, is no scope of its own: it shows every scope's missions and units (`global`, `matches(scope)`; stored as `*global`), and new missions are then created in Default (`scopeId` null); the archive then sends no `scope` (the API's `global` means Default's missions). New missions are created in it (`createMission` takes `scope`; `useMissionForm` and `useMapActions` pass it); Mission Details has a Scope select (Default plus the catalog's scopes; a deleted one is kept as an option by its ID): a new mission starts in the tab's scope, and changing it on an existing one PATCHes `scope` with the other edits on Save (not for a closed mission or offline). The Missions list's, the Map's, Active Missions' and the Mission Archive's option `currentScopeOnly` (Only the current scope, default on) shows only the selected scope's missions (the Map still shows the selected mission; the archive passes it to `useMissionArchive` and sends `scope`, an ID or `global`, to `/api/v1/missions/search`). `useMission(id)` finds one mission of any status, loading the closed ones only for an ID not among the others; one closed more than 24 h ago (the list leaves those out, the archive finds them) is fetched with `GET /api/v1/missions/{id}` (`useResource` with `persist: false`) and reported as `transient`; `useMissionData` uses it and loads such a mission's log entries, files and tasks in transient replica scopes (`scopeKey(table, id, { transient: true })`), kept in memory only, never in IndexedDB; their attachments' content paths are passed to `keepContentOut` (`offlineStore.ts`), so `requestCachedBlob` neither stores nor reads them. `useSelectedMission()` gives `{ mission, logEntries, logFiles, tasks, units }` for the dashboard's `selectedId` (mission null if it isn't a mission). `useMissionData(id)` gives the same for any other mission. The admin endpoints (users, groups, audit log) are loaded only by the admin widgets. Changes made elsewhere arrive through the event stream; still call `reload()` (or `cache.put`) after a write, so the writer sees it without waiting for the event.
