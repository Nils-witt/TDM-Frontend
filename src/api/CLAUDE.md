# src/api

Part of the root `CLAUDE.md` (Layout), kept here so it loads with this directory: the API modules, then offline mode (`connectivity.ts`, `offlineStore.ts`, `replica.ts`).

- `src/api/`: `layouts.ts` (dashboard layouts and the user's preferences), `client.ts` (`request` prefixes the API URL from `/config.json`, loaded by `main.tsx` before rendering: `apiBaseUrl` for OIDC (else `VITE_API_BASE_URL`), `mtlsApiBaseUrl` for client certificates (else `apiBaseUrl`); sends `credentials: 'include'` and the Bearer token, throws `ApiError` with the RFC 9457 `detail`; `request` gives up after `requestTimeout` (30 s; not for `FormData` uploads or `requestBlob`), which counts as no answer, so the app goes offline), `auth.ts` (`/auth/config`, `/api/v1/whoami`), `directory.ts` (users, groups, members), `audit.ts` (`auditLogPath`), `address.ts` (address suggestions from `/api/v1/address/{streets,house-numbers,cities,districts,geo-objects}`; the Object field suggests the directory's geo objects, and picking one replaces street, house number, city, district and position, and `reverseGeocode`, the address at a coordinate from `/api/v1/address/reverse` (the nearest address and nearest geo object): a geo object within 25 m (its name and address), else a house number within 50 m, else null; `nearbyPlaces`, the geo objects and house numbers nearest to a coordinate (`?limit=`) with their distance, behind the Mission Details' button beside Lat / Lon (`shared/NearbyPlaces.ts`, `NearbyPlacesButton`, `NearbyPlacesButtonMUI`), whose pick fills in the address but keeps the coordinates; a 404 turns them off until reload), `resource.ts` (`useResource(path)`: a shared, coalescing cache that loads when first shown, on `reload()` and on change events), `EventsProvider.tsx` + `events.ts` (live updates: a WebSocket to `GET /api/v1/events` (`websocketUrl` in `client.ts`) on which the API announces the entity types (table names) that changed; `changedPaths` maps them to API paths and `cache.reloadShown` reloads the shown ones, everything after a reconnect or `resync`. With OIDC the first message is `{"type":"auth","token":…}`, resent after each renewal (`accessTokenRenewed`), as a browser cannot set the Authorization header on a WebSocket; the client certificate proxy authenticates the upgrade itself. It reconnects with backoff; `LiveIndicator` in the menu bar (and the responsive UI's header) always shows the connection state: green when connected, red while disconnected). A new API entity type needs an entry in `typePaths`; unknown types reload everything, `setting.ts`, `maps.ts` (map styles: `useMapStyles()`, `resolveMapStyle`, `mapStylesApi`; overlays proxied by the API from its tile server: `useOverlays()`, `fetchOverlayBounds`, `overlayTilePath`; the admins' map defaults: `useMapSettings()`, `useDefaultOverlayStates()`). `useResource(path, fetcher)` takes an optional module-level fetcher; `list.ts` (`requestAll`, `listFetcher`) follows `next_before` through every page, and `collection.ts` (`useCollection`) turns a list into `{ items, byId, loading, error, reload }`. Types and paths per entity: `entity.ts`, `catalogs.ts` (plus `*Api` create/patch/remove for admins), `missions.ts`, `logbook.ts`, `tasks.ts`, `exportTemplates.ts` (`useExportTemplates()`, `exportTemplatesApi` incl. `preview`, `missionExportPath`), `reports.ts` (`useReports(filter)`, `reportsApi.create`/`sign`, `reportPdfPath`), `workflows.ts` (`useWorkflows()`, `useWorkflowCatalog()`, `workflowsApi`; admins only), `backup.ts` (`useBackupStatus()`: `GET /api/v1/backup-status`, which the API proxies from every go-backup-tool instance admins configure (`instances`, each with its shown `jobs` or an `error`), so the tokens stay on the server; polled every 60 s since go-backup-tool has no events; `summarizeBackup` gives `good`/`degraded`/`failed` across the instances, an unreadable one counting as one failure; `useBackupInstances()`, `backupInstancesApi` for `/api/v1/backup-instances` (admins only; the token is write-only, `has_token` says whether one is stored, a patch without it keeps it)). `/api/v1/users` is readable by every user (the Reports widget names signers with it). `units.ts` (`useUnits()`, `useUnitStatusChanges(limit)`: `GET /api/v1/units` and `/api/v1/units/status-changes`, the FMS statuses of the go-unit-mangement units server, which the API follows over that server's event stream and keeps in memory, so the changes start over when an API instance restarts (its first list records each unit's current status, `from` null); `enabled` false without `UNITS_URL`, `connected` false while the API's stream is down; reloaded on the event type `units`, which is not a table; `fmsStatusLabels`, `fmsTone`). FMS 0, 5 and 9 (`requestCodes`) are requests: the units server keeps the unit's status as it was and stores the latest report per unit and code (a new one replaces it, pending again even if acknowledged) as the unit's `requests` (`acknowledged_at`/`acknowledged_by` null while pending; the API's units-server account for acknowledgements made here), synced between units-server instances; the status changes list them as `request: true`, from the kept status to the code, and the workflow trigger Unit status changed fires for them (`trigger.request`). `acknowledgeUnitRequest` (`POST /api/v1/units/{id}/requests/{code}/acknowledge`, every user; 503 while the API is not connected to the units server). `missionUnits.ts`: units assigned to missions (`GET/POST /api/v1/mission-units`, `POST …/{id}/release`); a unit is on at most one mission at a time (the API answers 409 while it is on one, this or another, so it is released there first), releasing keeps the row as history, and closing a mission releases its units (an API trigger). A mission's rows come from the replica (`mission_units`, per mission, as `units` of `useMissionData`); `useActiveMissionUnits()` (`?active=true`, every current assignment, `byUnit`) tells which mission a unit is on. The unit's name and call sign are stored with the assignment for units the units server no longer knows. `unitScopes.ts`: the mission scope each unit is in (`GET /api/v1/unit-scopes`, `PUT /api/v1/unit-scopes/{unit_id}` with `{scope}`, `null` for Default; every user), at most one; the API lists no row for a unit in Default or one whose scope was deleted, and `unitScopeOf` also counts a scope missing from the catalog as Default; `useUnitScopes()` (`byUnit`, `set`, which puts the answer into the cache); event type `unit_scopes`.
- Offline mode (read-only): `api/connectivity.ts` counts the app offline while the event WebSocket is down or the last request got no answer (`useOffline()`, `offline()`); `send()` in `client.ts` then refuses non-GET requests. `api/offlineStore.ts` (IndexedDB via `idb`, database `universam-offline`, version 5; 4 added `mission_units`, 5 `scopes`) replicates the API's mission-domain tables (universalGoApi's `00004_missions.sql`): one store per table, named like it and like the event types (`missions`, `mission_type_groups`, `mission_types`, `logbook_types`, `file_types`, `scopes`, `log_entries`, `log_files`, `tasks`, `mission_units`), holding the API's rows keyed by `id`, with the table's indexes (`mission`, `entry`, `digest`, `group_id`, missions' `status`). `syncs` records when each scope was last synced. File contents loaded through `requestCachedBlob` are kept in `blobs` keyed by digest, as in the API, for log files the replica knows, so equal attachments are stored once. Others (report PDFs) go in `contents` by path; both stores share 100 MB, oldest evicted. `resources` keeps every other `useResource` path (the cache is created with `persist: true`: the stored copy shows until the first load answers; a load without an answer keeps the data without an error). `meta` keeps the last signed-in principal with the auth config. Scopes not synced for 24 h are dropped with their rows, and so is everything else older than that. `api/replica.ts` reads the mission domain local-first. `useTable<T>(scopeKey(table, value?))` (`useTables` joins several scopes of one table) returns a `Collection` of the stored rows at once and syncs the scope when first shown and on `reload()`: one `requestAll`, after which rows the API left out (revoked, deleted) are removed. `EventsProvider` calls `replica.syncShown(types)`. `replica.put`/`remove` apply a write's result (the Logbook removes a revoked entry and its files). The shown rows are also kept in memory, so the app works where IndexedDB is blocked. `ResourceProvider` provides the replica (`useReplica()`). `data/OfflinePrefetch.tsx` (in `DataProvider`) subscribes to the logbook, files and tasks of every mission that is not closed, so events keep them current, and downloads the contents of their attachments one at a time, skipping digests already stored. When `startSession()` gets no answer (network error, not an `ApiError`), it signs in as the stored user with `offline: true`; `App` then rechecks every 15 s, and on a 401 or token expiry starts the session again before ending it. Log Out, a 401 that ends the session, and another user signing in call `clearOffline()` (IndexedDB and the `map-tiles` cache). While offline `readOnly` of `useMissionData` / `useMissionForm` is true, the map's context menu does not open, the write actions of the nav, View menu, Reports and admin widgets are disabled, and `components/OfflineBanner` shows the time of the last API answer (floating on the desktop, at the top of `/m`'s content).
