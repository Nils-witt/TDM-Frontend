# src/responsive

Part of the root `CLAUDE.md` (Layout), kept here so it loads with this directory.

- `src/responsive/`: a responsive UI independent of the dashboard. It shares the data layer (`ResourceProvider` → `EventsProvider` → `DataProvider`, `src/api`, `src/data`), generic components and some widgets, but no dashboard, layouts, `DashboardContext` or selection. `AppFrame` has a header with the `LiveIndicator`, `BackupStatus` (the menu bar's `BackupIndicator` for phones: hidden unless enabled, colored by `summarizeBackup`; a tap opens the lazy `BackupStatusDialogMUI`, full screen on phones, with the same instances, jobs, expandable targets and Refresh; titles and labels shared in `nav/actions/backupLabels.ts`) and one nav that is a bottom tab bar on phones and a sidebar from 768px. `WidgetSheets` supplies `WidgetWindowContext`: what a widget opens in a window is a full-screen sheet kept in the history entry's state, so Back closes it. `EmbeddedWidget` shows a registered widget in a frame-like card that grows with the page. Routes (relative to `/m`, built with `paths.ts`): `missions` (`pages/MissionsPage`: search and status filter (Active, Done, Closed, All) kept in the URL as `?q=` and `?status=`, and a New button, disabled offline), `missions/new` (`pages/NewMissionPage`: `MissionFormMUI` without a mission, which creates one; the created mission's page then replaces it in the history), `missions/:id` (`pages/MissionPage`: a Show on map link (`paths.missionOnMap`, to `map?mission=`) for a mission with `address_coordinates`, the Mission Details widget's `MissionForm` for the mission in the URL, then the `LogbookForm` (`showMission: false`) and `Logbook` (`showCreate: false`) widgets (stacked; from 1100px the form left, the logbook right), given that mission through `SelectedMissionContext` with `useMissionData(id)`), `map` (`pages/MapPage`, lazy-loaded: the Map widget's `MissionMap` with its default options; tapping a pin keeps the mission in `?mission=` and shows a card linking to its page; it opens on the view it was left at, kept in `localStorage` (`universam.mapView`, `mapView.ts`) through `MissionMap`'s `onViewChange`). `archive` (`pages/ArchivePage`: the Mission Archive widget's `MissionArchiveMUI`; its filter, sort and page are kept in the URL (`MissionArchiveMUI/archiveUrl.ts`, passed to `useMissionArchive` as `state`), so Back from a result restores the search; a result opens the mission's page), `reports` (`pages/ReportsPage`: the Reports widget's `ReportsMUI` with Create, Upload signed and Share as MUI dialogs; `?mission=` (`paths.missionReports`, the Reports link on a done or closed mission's page) filters by it and is the mission Create offers first), `uhs` (the UHS view, only for UHS functions, whose only page it is (`uhs` in `responsive_pages`, not in `responsivePageIds`: the API sets it for UHS functions only; `FunctionPage`), so `homePath` is `/m/uhs`: `pages/UhsPage`, the patients currently in the session's UHS (`useSessionUhs()`), newest arrival first, with a search (`?q=`) and New Patient, and a second view Inbound (`?view=inbound`, chips with counts): those assigned from a mission and not yet there, each with an Arrived button that records the arrival (`patientsApi.arriveUhs`) and moves it to Patients (`useUhsPatients`' `arrived` / `inbound`); `uhs/new` (`pages/UhsNewPatientPage`: `PatientFormMUI`, a walk-in in the UHS, whose page then replaces it); `uhs/patients/:id` (`pages/UhsPatientPage`: `PatientFormMUI`, its missions by name, Arrived while it is inbound, its stays (with their arrival, by whom, and how they ended: `stayEndLabel`), Check out (a confirm dialog; only once arrived, `checkoutBlocker`: the patient was there and leaves) and Remove from UHS (assigned in error, never came), which asks for the required reason; after either, or on a 404, it returns to the list; its Transport section (`UhsTransportMUI`): the newest transport request (type, status, who requested it) with a button to its page, and Request transport (`transportBlocker`: once arrived, no open request), whose dialog picks a mission type offered for it (`transport_request`, "Group / Type") and then opens the transport's page); `uhs/patients/:id/transport` (`pages/UhsTransportPage`, `paths.uhsTransport`: `TransportDestinationMUI`, the request's mission read-only (type, status, the UHS's address, who requested it) and its destination on `AddressFieldsetMUI` with Save destination (If-Match the mission's version; a 412 reloads and says so), read-only once the mission is closed); the MUI parts in `widgets/UhsPatientsMUI/` on the desktop's `usePatientForm` and `useUhsPatients`; online only; the header's `ScopePicker` shows the UHS's name, as its scope is fixed), `settings` (`pages/SettingsPage`: account details from whoami, Map overlays, Desktop view, Log out). `ArchivePage`/`ReportsPage` are one `EmbeddedWidget` (`showHeading={false}`) below the page heading. The map's overlays are switched on the Settings page, not on the map: `overlaySettings.ts` keeps them in `localStorage` (`universam.mapOverlays`) and `MapPage` passes them as `overlayControl`. `MissionMap` takes `selectedId`/`onSelect` and an optional `overlayControl` (without it, its own state and switcher, as on the dashboard); the dashboard's `Map` widget wraps it with `useDashboard()`. The session's user function picks the sections (`views.responsive_pages` of whoami, `useAllowedViews().pages`): `sections.ts` holds them (Settings has no `page` and is always shown), `AppFrame` shows `visibleSections`, `ResponsiveShell` routes only those pages (Missions with `missions/new`; `missions/:id` always, as Map and Archive link to it), and `/m`, unknown and hidden paths go to `homePath`, the first shown section. The Settings page's Desktop view is hidden when the function has no desktop view. A new page gets a route in `ResponsiveShell`, a path in `paths.ts` and, if it is a section, an entry in `sections.ts` (and, if configurable, an ID in `responsivePageIds` (`api/sessions.ts`) and the API's `domain.ResponsivePages`). Widgets on `/m` are MUI (`@mui/material` 9 + emotion, styled with `sx`; icons stay `SymbolIcon`); the desktop does not use MUI. `src/responsive/widgets/` holds a `<Name>MUI` variant per widget used there (`MissionDetailsMUI` (`MissionFormMUI` only, used by `MissionPage`; the desktop wrapper needs `useDashboard()`), `LogbookFormMUI`, `LogbookMUI` (a visible Revoke button per entry instead of the context menu), `AttachmentViewerMUI`, `PdfViewerMUI`, `MissionArchiveMUI`, `ReportsMUI` (with `CreateReportDialogMUI`, `SignReportDialogMUI`, `ShareReportDialogMUI` on `shared/DialogsMUI`'s `DialogShell`, full screen on phones for `maxWidth="sm"`)) and their MUI inputs in `shared/`. They import the desktop widgets' hooks and helpers (`useMissionForm`, `useLogbookFormWidget`, `useLogbookWidget`, `logbookCommands`, `useAddressSuggest`, `useBlobContent`, `useMissionArchive`, `useReportsWidget`, `useCreateReport`, `useSignReport`, `useShareReport`, …) and only render differently, so a behavior change goes into the shared hook. `widgets/registry.ts` keys them by the desktop ID, reusing its metadata; `responsiveWidget(id)` (used by `EmbeddedWidget` and `WidgetSheets`) returns the MUI variant, else the desktop widget, so `openWidget('AttachmentViewer')` opens the MUI one on `/m`. The theme (`widgets/theme.ts`, colors from `_tokens.scss`, light/dark by system) is provided by `widgets/ThemeScope.tsx` and, like `MissionFormMUI`, loaded lazily so MUI stays out of the desktop's bundle. `_forms.scss`'s bare `input`/`select`/`textarea` rules skip elements with `Mui*` classes (via `:where`, keeping their specificity), as MUI's dialogs and poppers portal outside any route root.
